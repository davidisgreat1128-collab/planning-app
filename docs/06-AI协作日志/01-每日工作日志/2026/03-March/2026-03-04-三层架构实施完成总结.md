## 1. 项目概述

### 1.1 项目背景

Planning App 前端最初采用 **Component → Store → API** 两层架构：
- Component 调用 Store
- Store 直接调用 API（如 `getCategoriesApi()`）
- 缺少统一的数据管理层
- 离线场景无法正常工作

**核心问题**：
- 无法支持离线操作
- 数据不缓存，每次都请求服务器
- 无法处理网络断线重连
- 数据一致性难以保证

### 1.2 实施目标

实施 **Component → Store → Repository → API** 三层架构：

| 层级 | 职责 | 关键特性 |
|------|------|---------|
| Component | UI 渲染 + 用户交互 | 调用 Store actions |
| Store | 全局状态管理 + 业务逻辑 | 调用 Repository 方法 |
| Repository | 数据 CRUD + 持久化 + 离线队列 | memoryCache + localStorage + operationQueue |
| API | 后端接口 | RESTful 请求 |

**核心特性**：
- ✅ 离线优先（Offline-First）
- ✅ 乐观锁（Optimistic Locking）
- ✅ 指数退避重试（Exponential Backoff）
- ✅ 内存缓存 + 持久化缓存
- ✅ 自动同步服务器
- ✅ 操作队列（失败自动重试）

## 3. Repository 层详细分析

### 3.1 核心数据结构

所有 Repository（除 UserRepository）都包含以下数据结构：

```javascript
class BaseRepository {
  memoryCache = new Map();        // 内存缓存（主数据源）
  operationQueue = [];            // 离线操作队列
  retryTimeouts = new Map();      // 重试定时器
  syncDebounceTimer = null;       // 防抖定时器（500ms）
  isHydrated = false;             // 水合状态标志
}
```

**memoryCache（Map 结构）**：
- 键：实体 ID（字符串）
- 值：完整实体对象
- 优势：O(1) 查找性能

**operationQueue（数组）**：
```javascript
{
  id: 'op_1234567890_abc',        // 操作ID（唯一）
  type: 'create' | 'update' | 'delete',  // 操作类型
  entityId: 'CAT_1234567890',     // 实体ID
  data: { ... },                   // 操作数据
  retryCount: 0,                   // 重试次数
  timestamp: 1709568000000,        // 创建时间戳
  error: null                      // 最后一次错误
}
```

### 3.2 生命周期流程

#### hydrate() 启动流程

```javascript
async hydrate() {
  console.log('[Repository] 开始水合');

  // 1. 从 localStorage 加载缓存（同步操作）
  this._loadFromLocalStorage();

  // 2. 从服务器同步最新数据（异步操作）
  try {
    await this.sync();
  } catch (err) {
    console.warn('[Repository] 首次同步失败（离线？）:', err);
  }

  // 3. 重放离线队列（处理之前失败的操作）
  await this._replayQueue();

  this.isHydrated = true;
  console.log('[Repository] 水合完成，缓存条目:', this.memoryCache.size);
}
```

**为什么要三步**：
1. **先加载本地缓存**：让用户立即看到数据（即使离线）
2. **再同步服务器**：获取最新数据（如果在线）
3. **最后重放队列**：将之前失败的操作重新提交

#### create() 创建流程

```javascript
async create(data) {
  const entity = {
    id: this._generateId(),         // 生成唯一 ID
    ...data,
    version: 1,                     // 初始版本号
    createdAt: Date.now(),
    updatedAt: Date.now(),
    deletedAt: null                 // 软删除字段
  };

  // 1. 立即更新内存缓存（乐观更新）
  this.memoryCache.set(entity.id, entity);

  // 2. 添加到操作队列
  this._addToQueue({
    type: 'create',
    entityId: entity.id,
    data: entity
  });

  // 3. 保存到 localStorage
  this._saveToLocalStorage();

  // 4. 防抖同步服务器（500ms 后）
  this._debouncedSync();

  return entity;
}
```

**核心设计**：**乐观更新（Optimistic Update）**
- 用户点击"创建"立即看到结果（从 memoryCache 读取）
- 后台异步同步服务器
- 如果失败，进入重试队列（用户无感知）

#### update() 更新流程（含乐观锁）

```javascript
async update(id, changes) {
  const existing = this.memoryCache.get(id);
  if (!existing) {
    throw new Error('实体不存在');
  }

  const updated = {
    ...existing,
    ...changes,
    version: existing.version + 1,  // 版本号递增
    updatedAt: Date.now()
  };

  // 1. 乐观更新本地缓存
  this.memoryCache.set(id, updated);

  // 2. 添加到操作队列
  this._addToQueue({
    type: 'update',
    entityId: id,
    data: updated
  });

  // 3. 持久化 + 同步
  this._saveToLocalStorage();
  this._debouncedSync();

  return updated;
}
```

**乐观锁（Optimistic Locking）**：
- 每次更新，`version` 字段递增
- 服务器收到请求时，检查 `version` 是否匹配
- 如果不匹配（有人先修改了），返回 409 冲突错误
- 本地策略：**本地优先**（保留本地版本，忽略服务器版本）

#### _replayQueue() 重放队列（指数退避重试）

```javascript
async _replayQueue() {
  console.log('[Repository] 开始重放队列，待处理操作:', this.operationQueue.length);

  for (const op of [...this.operationQueue]) {  // 拷贝数组，避免遍历时修改
    try {
      await this._executeOperation(op);         // 执行操作
      this._removeFromQueue(op.id);             // 成功则移除
    } catch (err) {
      console.warn('[Repository] 操作失败，进入重试:', op.id, err);
      this._scheduleRetry(op);                  // 失败则安排重试
    }
  }
}

_scheduleRetry(op) {
  const delay = this._getRetryDelay(op.retryCount);  // 指数退避：1s, 2s, 4s, 8s, 16s

  if (op.retryCount >= 5) {
    console.error('[Repository] 达到最大重试次数，放弃:', op.id);
    op.error = '超过最大重试次数';
    this._saveToLocalStorage();  // 持久化错误状态（用户可稍后手动重试）
    return;
  }

  const timeoutId = setTimeout(async () => {
    op.retryCount++;
    try {
      await this._executeOperation(op);
      this._removeFromQueue(op.id);
    } catch (err) {
      this._scheduleRetry(op);  // 递归重试
    }
  }, delay);

  this.retryTimeouts.set(op.id, timeoutId);
}

_getRetryDelay(retryCount) {
  // 指数退避算法：1s → 2s → 4s → 8s → 16s
  return Math.min(1000 * Math.pow(2, retryCount), 16000);
}
```

**为什么使用指数退避**：
- 网络瞬断：1秒后重试（可能已恢复）
- 服务器过载：逐渐增加间隔，避免雪崩
- 长时间断网：16秒后仍失败，等待用户手动同步

### 3.3 防抖同步（Debounce Sync）

```javascript
_debouncedSync() {
  // 清除之前的定时器
  if (this.syncDebounceTimer) {
    clearTimeout(this.syncDebounceTimer);
  }

  // 500ms 后同步
  this.syncDebounceTimer = setTimeout(async () => {
    await this._replayQueue();
  }, 500);
}
```

**为什么需要防抖**：
- 用户连续创建10个分类 → 不要发10次请求
- 等待500ms，用户停止操作后，批量同步
- 减少服务器压力，提升用户体验

### 3.4 软删除（Soft Delete）

```javascript
async delete(id) {
  const existing = this.memoryCache.get(id);
  if (!existing) {
    throw new Error('实体不存在');
  }

  const deleted = {
    ...existing,
    deletedAt: Date.now(),        // 标记删除时间
    version: existing.version + 1
  };

  // 注意：不从 memoryCache 中移除，只标记 deletedAt
  this.memoryCache.set(id, deleted);

  this._addToQueue({
    type: 'delete',
    entityId: id,
    data: deleted
  });

  this._saveToLocalStorage();
  this._debouncedSync();

  return deleted;
}

getAll() {
  // 过滤掉已删除的实体
  return Array.from(this.memoryCache.values())
    .filter(item => !item.deletedAt)
    .sort((a, b) => a.sortOrder - b.sortOrder);
}
```

**为什么使用软删除**：
- 数据恢复：用户误删可以恢复
- 审计日志：保留删除记录
- 同步一致性：删除操作也需要同步到服务器

### 3.5 UserRepository 的简化设计

**为什么 UserRepository 不使用 operationQueue**：

| 场景 | UserRepository | 其他 Repository |
|------|---------------|----------------|
| 登录 | 必须立即成功或失败 | 可以离线稍后同步 |
| 登出 | 立即清除 token | 可以离线稍后同步 |
| 数据特点 | 单个用户的全局状态 | 可能有成百上千条记录 |
| 离线场景 | 访客模式（无需队列） | 需要队列保证数据不丢失 |

**UserRepository 核心代码**：

```javascript
class UserRepository {

  async login(credentials) {

    setStorage(config.TOKEN_KEY, result.token);
    setStorage(config.USER_INFO_KEY, JSON.stringify(result.user));
    removeStorage('guest_mode');
```

## 4. Store 层重构分析

### 4.1 Options API → Composition API

**重构前（Options API）**：

```javascript
export const useCategoryStore = defineStore('category', {
  state: () => ({
    categories: [],
    loading: false
  }),

  getters: {
    allCategories(state) {
      return state.categories;
    }
  },

  actions: {
    async fetchCategories() {
      this.loading = true;
      try {
        const res = await getCategoriesApi();
        this.categories = res;
      } finally {
        this.loading = false;
      }
    }
  }
});
```

**重构后（Composition API）**：

```javascript
export const useCategoryStore = defineStore('category', () => {
  // State（响应式变量）
  const loading = ref(false);

  // Getters（计算属性，自动从 Repository 获取）
  const categories = computed(() => {
    return CategoryRepository.getAll();  // 自动同步
  });

  // Actions（函数）
  async function hydrate() {
    loading.value = true;
    try {
      await CategoryRepository.hydrate();  // 调用 Repository
    } finally {
      loading.value = false;
    }
  }

  async function createCategory(data) {
    const category = await CategoryRepository.create(data);
    // 无需手动更新 categories，computed 会自动触发
    return category;
  }

  return { categories, loading, hydrate, createCategory };
});
```

**关键变化**：
1. `state` → `ref()` / `reactive()`
2. `getters` → `computed()`
3. `actions` → `async function()`
4. **categories 从数组变为 computed 属性**（自动同步 Repository）

### 4.2 computed 属性自动同步

**核心机制**：

```javascript
// Store
const categories = computed(() => {
  return CategoryRepository.getAll();  // 每次访问都调用 getAll()
});

// Repository
getAll() {
  return Array.from(this.memoryCache.values())
    .filter(item => !item.deletedAt)
    .sort((a, b) => a.sortOrder - b.sortOrder);
}
```

**数据流**：
```
CategoryRepository.create(data)
  → memoryCache.set(id, category)
  → Store.categories（computed 自动重新计算）
  → Component（Vue 响应式系统自动重新渲染）
```

**优势**：
- 无需手动 `this.categories.push(newCategory)`
- 单向数据流：Repository 是唯一数据源
- 避免状态不一致

### 6.2 数据流向详解

#### 读取数据流（App 启动时）

```
1. 用户打开 App
    ↓
2. App.vue onLaunch()
    ↓
3. Promise.all([
     categoryStore.hydrate(),
     taskStore.hydrate(),
     userStore.hydrate(),
     logStore.hydrate(),
     planningStore.hydrate()

    ↓
4. categoryStore.hydrate()
    ↓

    │      → for (category of res) { memoryCache.set(id, category) }
    │
    └─ 5.3 _replayQueue()                  （重放离线队列）
```

#### 离线场景数据流（网络断开时）

```
1. 用户点击"添加分类"（此时网络已断开）
    ↓
2-6. 同上（步骤1-6完全相同）
    → 用户立即看到新分类（因为是乐观更新）
    ↓
7. 500ms 后，_replayQueue() 触发
    ↓
8. _executeOperation(op)
    → const res = await createCategoryApi(op.data)
    ↓
9. 请求失败（Network Error）
    → catch (err) { ... }
    ↓
10. _scheduleRetry(op)
    ├─ 计算重试延迟：delay = 1000 * 2^0 = 1s
    ├─ setTimeout(() => { retry }, 1000)
    └─ op.retryCount++  （0 → 1）
    ↓
11. 1秒后重试
    → 再次失败（网络仍断开）
    → delay = 1000 * 2^1 = 2s
    ↓
12. 2秒后重试
    → 再次失败
    → delay = 1000 * 2^2 = 4s
    ↓
13. 4秒后重试
    → 成功！（网络已恢复）
    → _removeFromQueue(op.id)
    ↓
14. 同步完成！
```

**关键设计**：
- 用户在第1步点击后，**立即看到结果**（乐观更新）
- 即使网络断开，用户也**无感知**（前端继续工作）
- 网络恢复后，**自动同步**（无需用户干预）

#### 冲突处理数据流（乐观锁场景）

```
场景：用户A和用户B同时编辑同一分类

1. 初始状态（服务器）：
   { id: 'CAT_001', name: '工作', color: '#FF0000', version: 5 }

2. 用户A 在手机上修改
   → CategoryRepository.update('CAT_001', { name: '工作计划' })
   → 本地缓存：{ ..., name: '工作计划', version: 6 }  （本地先改）
   → 入队：{ type: 'update', data: { ..., version: 6 } }

3. 用户B 在电脑上修改（同时进行）
   → CategoryRepository.update('CAT_001', { color: '#00FF00' })
   → 本地缓存：{ ..., color: '#00FF00', version: 6 }
   → 入队：{ type: 'update', data: { ..., version: 6 } }

4. 用户A 的操作先到达服务器
   → PUT /api/v1/categories/CAT_001
   → body: { name: '工作计划', version: 6 }
   → 服务器检查：version 6 > 当前版本 5 ✓ 允许更新
   → 服务器更新：{ ..., name: '工作计划', version: 6 }
   → 返回 200 OK

5. 用户B 的操作随后到达服务器
   → PUT /api/v1/categories/CAT_001
   → body: { color: '#00FF00', version: 6 }
   → 服务器检查：version 6 == 当前版本 6 ✗ 冲突！
   → 返回 409 Conflict { message: '版本冲突', serverVersion: 6 }

6. 用户B 的客户端收到 409
   → _executeOperation() catch (err)
   → if (err.code === 409) {
       console.warn('[Repository] 版本冲突，采用本地优先策略');
       // 策略：保留本地版本，不再重试
       _removeFromQueue(op.id);
     }

7. 最终状态
   → 服务器：{ id: 'CAT_001', name: '工作计划', color: '#FF0000', version: 6 }
   → 用户A 本地：同服务器
   → 用户B 本地：{ ..., name: '工作', color: '#00FF00', version: 6 }  （本地修改保留）
```

**本地优先策略**：
- 当发生冲突时，保留本地修改（因为这是用户最新的意图）
- 不覆盖本地数据（避免用户刚修改的内容被覆盖）
- 下次 sync() 时，用户B 会看到服务器版本，可手动解决冲突

### 6.3 Repository 内部状态机

```
┌─────────────────────────────────────────────────────────────────────┐
│                   Repository 内部状态机                               │
└─────────────────────────────────────────────────────────────────────┘

状态1：未初始化（isHydrated = false）
    ├─ memoryCache: Map { size: 0 }
    ├─ operationQueue: []
    └─ retryTimeouts: Map { size: 0 }
    ↓
    调用 hydrate()
    ↓
状态2：正在水合（isHydrated = false, loading = true）
    ├─ 步骤1：_loadFromLocalStorage()
    │    → memoryCache 填充本地缓存（可能有10条旧数据）
    │
    ├─ 步骤2：sync()
    │    → 从服务器拉取最新数据（可能有12条，新增2条）
    │    → memoryCache 更新为12条
    │
    └─ 步骤3：_replayQueue()
         → 重放之前失败的操作（可能队列中有3条待同步）
         → 成功2条 → 移除队列
         → 失败1条 → 安排重试
    ↓
状态3：已水合（isHydrated = true, loading = false）
    ├─ memoryCache: Map { size: 12 }  （12条分类）
    ├─ operationQueue: [op1]          （1条失败操作，正在重试）
    └─ retryTimeouts: Map { 'op1' => timeout }
    ↓
    用户操作：create / update / delete
    ↓
状态4：有待同步操作（isHydrated = true, queue.length > 0）
    ├─ memoryCache: Map { size: 13 }  （新增1条分类）
    ├─ operationQueue: [op1, op2]     （op1旧的失败操作，op2新的创建操作）
    └─ retryTimeouts: Map { 'op1' => timeout }
    ↓
    500ms 后，_debouncedSync() 触发
    ↓
状态5：正在同步（isHydrated = true, syncing = true）
    → _replayQueue() 遍历队列
    → _executeOperation(op1) → 成功 → 移除
    → _executeOperation(op2) → 成功 → 移除
    ↓
状态6：同步完成（isHydrated = true, queue.length = 0）
    ├─ memoryCache: Map { size: 13 }
    ├─ operationQueue: []             （队列清空）
    └─ retryTimeouts: Map { size: 0 }
    ↓
    （循环回状态3）
```

**异常状态**：

```
状态X：网络断开（isHydrated = true, offline = true）
    ├─ memoryCache: Map { size: 13 }  （本地缓存继续工作）
    ├─ operationQueue: [op1, op2, op3, op4, op5]  （队列堆积）
    └─ retryTimeouts: Map { ... }      （多个重试定时器）
    ↓
    每次操作都会：
    1. 立即更新 memoryCache（用户无感知）
    2. 入队
    3. 尝试同步 → 失败 → 指数退避重试
    ↓
    网络恢复
    ↓
    最近的一次重试成功 → 触发 _replayQueue()
    → 批量提交所有堆积的操作
    → 队列清空
    ↓
    （恢复到状态6）
```

## 7. 设计模式总结

### 7.1 使用的设计模式

#### 1. Repository 模式（Repository Pattern）

**定义**：在数据源（如数据库、API）和业务逻辑之间添加一个抽象层。

**实现**：
```javascript
// Store 不关心数据从哪来（API？localStorage？IndexedDB？）
// 只调用 Repository 的接口
const category = await CategoryRepository.create(data);

// Repository 内部决定：
// 1. 先更新 memoryCache（内存）
// 2. 再更新 localStorage（持久化）
// 3. 最后同步 API（服务器）
```

**优势**：
- 解耦：Store 不依赖具体的数据源
- 可测试：可以 mock Repository，无需真实 API
- 可扩展：未来可以换成 IndexedDB，Store 无需改动

#### 2. 单例模式（Singleton Pattern）

**定义**：确保一个类只有一个实例，并提供全局访问点。

**实现**：
```javascript
// CategoryRepository.js
class CategoryRepository {
  constructor() { ... }
}

// 导出唯一实例（ES Module 天然单例）
export default new CategoryRepository();

// 所有模块引用的是同一个实例
import CategoryRepository from '@/repositories/CategoryRepository.js';
```

**优势**：
- memoryCache 全局共享（所有 Store 看到的是同一份数据）
- operationQueue 全局共享（避免重复操作）

#### 3. 命令模式（Command Pattern）

**定义**：将请求封装为对象，支持撤销、重做、队列化。

**实现**：
```javascript
// 每个操作封装为 Operation 对象
const operation = {
  id: 'op_1234567890_abc',
  type: 'create',              // 命令类型
  entityId: 'CAT_001',
  data: { name: '工作' },      // 命令参数
  retryCount: 0,
  timestamp: 1709568000000
};

// 入队
operationQueue.push(operation);

// 执行
await _executeOperation(operation);

// 撤销（移除队列）
_removeFromQueue(operation.id);
```

**优势**：
- 支持离线队列（延迟执行）
- 支持重试（失败后重新执行）
- 支持撤销（未实现，但架构支持）

#### 4. 观察者模式（Observer Pattern）

**定义**：对象间的一对多依赖，当一个对象状态改变时，所有依赖者都会收到通知。

**实现**：
```javascript
// Repository 是被观察者（Subject）
memoryCache.set(id, category);  // 状态改变

// Store 的 computed 是观察者（Observer）
const categories = computed(() => {
  return CategoryRepository.getAll();  // 自动订阅变化
});

// Vue 响应式系统是观察者（Observer）
// computed 变化 → Component 自动重新渲染
```

**优势**：
- 自动同步：Repository 变化 → Store 自动更新 → Component 自动渲染
- 解耦：Repository 不知道有哪些 Store 在使用它

#### 5. 策略模式（Strategy Pattern）

**定义**：定义一系列算法，将每个算法封装起来，使它们可以互换。

**实现**：
```javascript
// 重试策略：指数退避
_getRetryDelay(retryCount) {
  return Math.min(1000 * Math.pow(2, retryCount), 16000);
}

// 未来可以换成线性退避
_getRetryDelay(retryCount) {
  return Math.min(1000 * retryCount, 10000);
}

// 或者固定间隔
_getRetryDelay(retryCount) {
  return 3000;
}
```

**优势**：
- 可配置：不同的 Repository 可以使用不同的重试策略
- 可扩展：新增策略无需修改核心代码

#### 6. 适配器模式（Adapter Pattern）

**定义**：将一个类的接口转换为客户期望的另一个接口。

**实现**：
```javascript
// Store 期望的接口
categoryStore.createCategory({ name: '工作' });

// Repository 提供的接口
CategoryRepository.create({ name: '工作', color: '#FF0000' });

// Store 作为适配器
async function createCategory(data) {
  // 添加默认值
  const fullData = {
    color: '#999999',
    icon: 'folder',
    ...data
  };
  return await CategoryRepository.create(fullData);
}
```

**优势**：
- Store 可以封装业务逻辑（如默认值、校验）
- Repository 保持通用性

### 7.2 架构原则

#### SOLID 原则

**S - 单一职责原则（Single Responsibility Principle）**：
- ✅ Component：只负责 UI 渲染
- ✅ Store：只负责状态管理和业务逻辑
- ✅ Repository：只负责数据 CRUD 和持久化

**O - 开闭原则（Open-Closed Principle）**：
- ✅ 新增 Repository 无需修改现有代码
- ✅ 新增 Store 无需修改 Repository
- ✅ 新增 Component 无需修改 Store

**L - 里氏替换原则（Liskov Substitution Principle）**：
- ✅ 所有 Repository 实现统一接口（hydrate / getAll / create / update / delete）
- ✅ 可以用 MockRepository 替换 CategoryRepository 进行测试

**I - 接口隔离原则（Interface Segregation Principle）**：
- ✅ LogRepository 提供 convertToTask()，其他 Repository 不需要
- ✅ PlanningRepository 提供 getByType()，其他 Repository 不需要

**D - 依赖倒置原则（Dependency Inversion Principle）**：
- ✅ Store 依赖 Repository 接口，不依赖具体实现
- ✅ Repository 依赖 API 接口，不依赖具体后端框架

#### 其他原则

**DRY（Don't Repeat Yourself）**：
- ✅ 所有 Repository 共享相同的核心代码（memoryCache / operationQueue / retry）
- ✅ 未来可以抽象为 BaseRepository 基类

**KISS（Keep It Simple, Stupid）**：
- ✅ UserRepository 简化设计（无 operationQueue）
- ✅ PlanningRepository 使用伪分页（无需真实分页）

**YAGNI（You Aren't Gonna Need It）**：
- ✅ 没有实现用户不需要的功能（如撤销、冲突合并 UI）
- ✅ 企业级架构文档标注⏸️待办（DTO / Validator / RepositoryFactory）

## 8. 经验教训

### 8.1 成功经验

#### 1. 文档先行（Documentation-First）

**做法**：
- 第15次会话先创建 `三层架构设计.md`（600行）
- 包含完整的 CategoryRepository 示例代码（285行）
- 明确迁移检查清单和 FAQ

**效果**：
- 后续实施 4 个 Repository 全部按照文档执行
- 代码风格高度一致
- 减少返工（无需反复修改设计）

**教训**：
> **重大架构变更，必须先写设计文档，再写代码。**

#### 2. 增量实施（Incremental Implementation）

**做法**：
- 先实施 CategoryRepository（最简单）
- 再实施 TaskRepository（复杂业务逻辑）
- 再实施 UserRepository（特殊设计）
- 最后实施 LogRepository 和 PlanningRepository（完整特性）

**效果**：
- 每个 Repository 完成后立即提交（10个 commit）
- 每次提交都是可工作的状态
- 出现问题可以快速定位到具体 commit

**教训**：
> **大型重构，必须分步实施，每步都提交可工作的代码。**

#### 3. 计算属性自动同步（Computed Auto-Sync）

**做法**：
```javascript
// Store 中，将数据列表改为 computed 属性
const categories = computed(() => {
  return CategoryRepository.getAll();
});
```

**效果**：
- 无需手动 `this.categories.push(newCategory)`
- Repository 是唯一数据源（避免状态不一致）
- Vue 响应式系统自动处理渲染

**教训**：
> **在 Repository 模式中，Store 的数据列表应该是 computed 属性，而不是 state。**

#### 4. 乐观更新（Optimistic Update）

**做法**：
```javascript
async create(data) {
  const entity = { id, ...data };
  this.memoryCache.set(id, entity);  // 立即更新缓存
  this._addToQueue({ ... });         // 后台同步
  return entity;                     // 立即返回
}
```

**效果**：
- 用户点击"创建"立即看到结果（无需等待服务器响应）
- 应用"感觉"像本地应用（即使网络慢）
- 离线场景无缝工作

**教训**：
> **离线优先架构的核心是乐观更新：先本地，后服务器。**

#### 5. 指数退避重试（Exponential Backoff）

**做法**：
```javascript
_getRetryDelay(retryCount) {
  return Math.min(1000 * Math.pow(2, retryCount), 16000);
}
```

**效果**：
- 网络瞬断：1秒后重试（快速恢复）
- 服务器过载：逐渐增加间隔（避免雪崩）
- 长时间断网：16秒后停止（避免无限重试）

**教训**：
> **重试必须使用指数退避，避免固定间隔造成"惊群效应"。**

### 8.2 遇到的问题和解决方案

#### 问题1：UserRepository 是否需要 operationQueue？

**初始设计**：所有 Repository 都使用相同设计（包括 operationQueue）

**问题**：
- 用户登录必须立即成功或失败（不能延迟）
- 访客模式需要立即切换（不能入队）
- 登出操作必须立即生效（不能重试）

**解决方案**：UserRepository 简化设计
- 移除 memoryCache / operationQueue
- 直接操作 localStorage
- 登录/登出直接调用 API（同步）

**教训**：
> **不要教条地套用模式。根据实际需求，灵活调整设计。**

#### 问题2：Store 的 list 是 state 还是 computed？

**初始设计**：
```javascript
const categories = ref([]);  // state

async function createCategory(data) {
  const category = await CategoryRepository.create(data);
  categories.value.push(category);  // 手动同步
}
```

**问题**：
- Store 和 Repository 都存储数据（双数据源）
- 容易出现状态不一致
- 刷新页面后，Store 的 state 丢失

**解决方案**：改为 computed 属性
```javascript
const categories = computed(() => {
  return CategoryRepository.getAll();  // 自动同步
});

async function createCategory(data) {
  const category = await CategoryRepository.create(data);
  // 无需手动同步，computed 会自动触发
  return category;
}
```

**教训**：
> **Repository 是唯一数据源。Store 的 list 应该是 computed 属性，而不是 state。**

#### 问题3：乐观锁冲突如何处理？

**场景**：用户A和用户B同时编辑同一分类

**初始方案**：服务器返回 409 → 抛出错误 → 提示用户"版本冲突，请刷新"

**问题**：
- 用户体验差（刚编辑的内容要重新输入）
- 无法自动解决冲突

**解决方案**：**本地优先策略**
```javascript
if (err.code === 409) {
  console.warn('[Repository] 版本冲突，采用本地优先策略');
  // 保留本地版本，不覆盖用户的修改
  _removeFromQueue(op.id);  // 移除队列，不再重试
}
```

**教训**：
> **乐观锁冲突时，优先保留用户的本地修改，而不是覆盖为服务器版本。**

#### 问题4：LogRepository 同步历史数据过多

**场景**：用户使用 App 1年，日志有 365 条

**初始方案**：`sync()` 拉取所有日志
```javascript
async sync() {
  const res = await getLogsApi();  // 拉取所有日志（365条）
  // ...
}
```

**问题**：
- 首次同步慢（需要下载 365 条记录）
- memoryCache 占用内存大
- localStorage 超出 5MB 限制

**解决方案**：只同步最近30天
```javascript
async sync() {
  const endDate = new Date().toISOString().split('T')[0];
  const startDate = new Date(Date.now() - 30 * 24 * 60 * 60 * 1000)
    .toISOString().split('T')[0];

  const res = await getLogsApi({ start: startDate, end: endDate });
  // 只缓存最近30天（约30条）
}
```

**教训**：
> **历史数据不需要全部缓存。根据业务需求，只缓存最近的数据。**

#### 问题5：Planning Store 的分页如何处理？

**场景**：原有 Store 使用真实分页（page / pageSize / loadMore）

**问题**：
- Repository 已在 hydrate() 时缓存所有规划
- 前端分页变成多余操作（每次 loadMore 都请求服务器）
- 用户体验反而变差（需要等待请求）

**解决方案**：改为伪分页
```javascript
const pagination = computed(() => {
  return {
    page: 1,        // 固定为1
    pageSize: 20,
    total: list.value.length,
    totalPages: Math.ceil(list.value.length / 20)
  };
});

async function loadMore() {
  // Repository 模式下无需分页，直接返回
  console.log('[PlanningStore] Repository 模式无需分页');
  return;
}
```

**教训**：
> **Repository 缓存所有数据后，前端分页变成伪分页（只影响视觉，不影响性能）。**

### 9.2 测试建议

#### 单元测试（Repository 层）

```javascript
// tests/unit/repositories/CategoryRepository.spec.js
import CategoryRepository from '@/repositories/CategoryRepository.js';

describe('CategoryRepository', () => {
  beforeEach(() => {
    // 清空缓存
    CategoryRepository.memoryCache.clear();
    CategoryRepository.operationQueue = [];
    localStorage.clear();
  });

  test('create() 应该立即更新 memoryCache', async () => {
    const category = await CategoryRepository.create({ name: '工作' });

    expect(CategoryRepository.memoryCache.has(category.id)).toBe(true);
    expect(CategoryRepository.memoryCache.get(category.id).name).toBe('工作');
  });

  test('create() 应该入队', async () => {
    const category = await CategoryRepository.create({ name: '工作' });

    expect(CategoryRepository.operationQueue.length).toBe(1);
    expect(CategoryRepository.operationQueue[0].type).toBe('create');
```

```javascript
class UndoManager {
  undoStack = [];
  redoStack = [];

  record(action) {
    this.undoStack.push(action);
    this.redoStack = [];  // 清空重做栈
  }

  undo() {
    const action = this.undoStack.pop();
    if (action) {
      action.undo();  // 执行撤销
      this.redoStack.push(action);
    }
  }

  redo() {
    const action = this.redoStack.pop();
    if (action) {
      action.redo();  // 执行重做
      this.undoStack.push(action);
    }
  }
}

// 使用
await CategoryRepository.create(data);

  undo: () => CategoryRepository.delete(data.id),
  redo: () => CategoryRepository.create(data)
});
```
