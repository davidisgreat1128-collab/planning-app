**任务位置计算**:
```javascript
function calculateTaskTop(task) {
  const [hour, minute] = task.startTime.split(':').map(Number);

  // 每个小时格100rpx，每分钟约 1.67rpx（100/60）
  const topInHour = (minute / 60) * 100;

  return topInHour;
}

function calculateTaskHeight(task) {
  const [startHour, startMinute] = task.startTime.split(':').map(Number);
  const [endHour, endMinute] = task.endTime ? task.endTime.split(':').map(Number) : [startHour, startMinute + 30];

  const startTotalMinutes = startHour * 60 + startMinute;
  const endTotalMinutes = endHour * 60 + endMinute;
  const durationMinutes = endTotalMinutes - startTotalMinutes;

  // 每分钟约 1.67rpx，最小高度50rpx
  return Math.max((durationMinutes / 60) * 100, 50);
}
```

**当前时间红线位置**:
```javascript
function updateCurrentTime() {
  const now = new Date();
  currentHour.value = now.getHours();
  currentMinute.value = now.getMinutes();

  // 全天区域高度约200rpx + 每小时100rpx
  const alldayHeight = 200;
  const hourHeight = 100;

  currentTimeTop.value = alldayHeight + (currentHour.value * hourHeight) + (currentMinute.value / 60 * hourHeight);

  // 自动滚动到当前时间（仅首次加载）
  if (showCurrentTimeLine.value && scrollTop.value === 0) {
    scrollTop.value = Math.max(0, currentTimeTop.value - 400); // 偏移400rpx使红线在屏幕中部
  }
}
```

### 决策1: 为什么创建 TaskCard 组件？

**解决方案**: 创建独立的 TaskCard 组件

**优势**:
1. **代码复用**: 一次编写，多处使用
2. **样式统一**: 保证所有视图中的任务卡片样式一致
3. **易于维护**: 修改一处，全局生效
4. **可测试性**: 独立组件易于编写单元测试

**示例**:

  v-for="task in notUrgentImportant"

### 决策2: 为什么 index.vue 还有 797 行？

**目标**: 减少到 <500 行

**实际**: 797 行（超出 297 行）

**原因分析**:
1. **模板行数**: 226 行（包含3个视图 + 多个弹窗）
2. **脚本行数**: 227 行（包含18个方法 + 计算属性）
3. **样式行数**: 344 行（包含所有布局和弹窗样式）

**为什么不继续拆分？**:
- **模板部分**: 已经使用组件化（CalendarBar、TaskQuadrantView、TimelineView、TaskCard），剩余的是页面级逻辑（顶部栏、FAB、弹窗），无法进一步拆分
- **脚本部分**: 已经使用 Composables（useCalendar、useDragDrop、useTaskQuadrant），剩余的是页面级协调逻辑，必须保留在 index.vue
- **样式部分**: 可以拆分到独立的 `.scss` 文件，但 UniApp 推荐使用 scoped CSS，拆分会降低可读性

**结论**: 797 行是一个合理的平衡点，相比原来 3728 行已经减少了 78.6%，且代码结构清晰，易于维护。

## 💡 经验总结

### 成功经验

1. **分阶段重构策略**
   - Stage 1: Composables 提取
   - Stage 2: Utils 提取
   - Stage 3: 组件拆分
   - Stage 4: index.vue 最终重构
   - 这种分阶段策略使得每一步都可控、可测试、可回滚

2. **先提取逻辑，再提取UI**
   - 先提取 Composables 和 Utils（纯逻辑）
   - 再提取 Components（UI）
   - 最后重构 index.vue（协调层）
   - 这种顺序避免了逻辑和UI的相互依赖

3. **保持 Git commit 的原子性**
   - Commit 1: 3 个组件（独立功能）
   - Commit 2: index.vue 重构（完整功能）
   - 每个 commit 都是一个可运行的完整状态

4. **使用 TypeScript JSDoc**
   - 虽然项目使用 JavaScript，但通过 JSDoc 提供类型提示
   - 提高代码可读性和 IDE 支持

5. **遵循三层架构**
   - Component（UI） → Composable（业务逻辑） → Store（状态管理） → Repository（数据访问）
   - 每一层都有明确的职责

### 遇到的挑战

1. **Composable 的 ref 访问**
   - **问题**: 在模板中访问 Composable 的 ref 需要 `.value`
   - **解决**: 使用 `calendarComposable.selectedDate.value`
   - **未来优化**: 可以使用 `toRefs()` 解构

2. **handleDrop 函数的 forward reference**
   - **问题**: `useDragDrop({ onDrop: handleDrop })` 但 `handleDrop` 在后面定义
   - **解决**: JavaScript 的函数提升机制自动解决
   - **注意**: 如果使用箭头函数则需要调整顺序

3. **组件通信的复杂性**
   - **问题**: TaskCard → TaskQuadrantView → index.vue 的事件传递
   - **解决**: 使用标准的 Props Down / Events Up 模式
   - **优化**: 可以考虑使用 `provide/inject` 简化深层通信
