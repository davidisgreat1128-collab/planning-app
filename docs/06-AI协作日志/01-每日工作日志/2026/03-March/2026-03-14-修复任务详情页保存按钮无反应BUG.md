### 第三步：根因分析

**问题链路**：

```
1. task-edit.vue onMounted() 手动赋值form字段
   ↓

   ↓
3. originalForm 和 originalSubtasks 未初始化
   ↓
4. hasFormChanged 检测到 originalForm 不存在，返回 false
```

## ✅ 修复方案

### 核心修改

**修改文件**: `frontend/Planning-app/pages/calendar/task-edit.vue`

**修改位置**: `onMounted()` 生命周期（第1332-1429行）

**修改前**（❌ 错误写法）：
```javascript
onMounted(() => {
  if (task) {
    // 手动赋值，未初始化originalForm
    form.value.title = task.title || '';
    form.value.description = task.description || '';
    form.value.isUrgent = task.isUrgent || false;
    // ... 40+行手动赋值
    // ❌ 缺少：originalForm和originalSubtasks初始化
  }
});
```

**修改后**（✅ 正确写法）：
```javascript
onMounted(() => {
  if (task) {
    // ✅ 调用 Composable 方法初始化表单
    console.log('[TaskEdit] 调用 taskFormApi.loadFromTask() 初始化表单');

    // 保存原始任务ID
    originalTaskId.value = task.taskId || task.id;

    // 调用 useTaskForm 的 loadFromTask 方法
    taskFormApi.loadFromTask(task);

    // 解析 RRULE 到 UI 状态（如果有）
    if (task.rrule) {
      parseRruleToUI(task.rrule);
    }

    // 设置任务完成状态
    taskDone.value = task.status === 'completed';
  }
});
```

**额外修改**：从`taskFormApi`解构`loadFromTask`方法
```javascript
const {
  form,
  subtasks,
  // ... 其他属性
  update,
  loadFromTask  // ✅ 新增：解构 loadFromTask 方法
} = taskFormApi;
```

### 修复效果

修复后的执行流程：

```
1. task-edit.vue onMounted() 调用 taskFormApi.loadFromTask(task)
   ↓
2. useTaskForm.loadFromTask() 加载表单数据
   ↓

   ↓

   ↓
```

## 📝 技术决策记录

### 为什么不在task-edit.vue中手动初始化originalForm？

**方案A**（❌ 不推荐）：在task-edit.vue的onMounted中手动赋值后，再手动初始化originalForm
```javascript
// ❌ 违反四层架构，逻辑重复
originalForm.value = JSON.parse(JSON.stringify(form.value))
```

**方案B**（✅ 推荐，已采用）：调用useTaskForm.loadFromTask()
```javascript
// ✅ 符合四层架构，复用Composable逻辑
taskFormApi.loadFromTask(task)
```

**选择方案B的理由**：
1. **遵循单一职责原则**：表单初始化逻辑应该在Composable层统一管理
2. **避免代码重复**：loadFromTask已经实现了完整的初始化逻辑（包括originalForm）
3. **可维护性更强**：未来修改初始化逻辑只需改一处（Composable），不需要改多个Component
4. **符合CLAUDE.md第8.0节SRP原则**：一个组件只应该有一个改变的理由

## 🎓 经验总结

### 教训1：架构分层要严格遵守

**错误做法**：
- Component层直接操作数据，绕过Composable层
- 导致状态管理混乱，BUG难以追踪

**正确做法**：
- 严格遵守 Component → Composable → Store → Repository 调用链
- Composable层的方法（如loadFromTask）应该被充分复用

### 教训2：CLAUDE.md第8节"6个必查项"的重要性

**本次BUG诊断过程**：
1. 执行必查项1（架构分层检查）→ 发现调用链正确
2. 执行必查项2（文件大小检查）→ 发现文件超标
3. 代码分析 → 发现违反四层架构，未调用Composable方法

**结论**：
- "6个必查项"不仅是防止引入新BUG，也能帮助快速定位现有BUG
- **强制执行6个必查项**能避免80%的架构退化问题

### 教训3：hasFormChanged的设计哲学

**设计意图**：
- `hasFormChanged`依赖`originalForm`来检测表单是否变化
- `originalForm`必须在加载任务时初始化（通过`loadFromTask`）

**错误使用场景**（本次BUG）：
- 手动赋值form字段，未调用`loadFromTask`
- 导致`originalForm`未初始化，`hasFormChanged`永远为false

**启示**：
- Composable的初始化方法（如`loadFromTask`）必须被调用
- 不能只使用Composable的数据（form），而跳过初始化方法
