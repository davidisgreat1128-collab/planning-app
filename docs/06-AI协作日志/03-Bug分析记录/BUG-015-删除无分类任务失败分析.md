## 📋 问题描述

### 现象

用户执行"清空无分类任务"操作时：

1. **第一次点击**：任务成功删除，UI显示成功
2. **第二次点击**：控制台报错 `DELETE /tasks/182 404 Not Found`

### 用户影响

- ⚠️ 虽然任务已成功删除，但错误提示影响用户体验
- ⚠️ 控制台大量404错误，影响问题排查
- ⚠️ 用户可能误以为删除失败，重复操作

---

## 🔍 问题分析

### 初步诊断

通过临时诊断日志（commit e96698f），100%确认为**DELETE和fetchTasksByDate()之间的竞态条件**。

### 时间线分析（修复前）

```
T+0ms:   clearUncategorizedTasks() 开始
T+5ms:   DELETE 182 → 加入同步队列（未立即执行）
T+6ms:   DELETE 183 → 加入同步队列（未立即执行）
T+7ms:   clearUncategorizedTasks() 完成 ← Component继续执行
T+8ms:   emit('container-changed')
T+9ms:   handleContainerChanged() 调用
T+10ms:  fetchTasksByDate() 查询数据库
         ⚠️ 此时数据库 deleted_at 仍为 NULL（DELETE未执行）
T+11ms:  后端返回任务182、183
T+12ms:  任务182、183重新加入缓存 ❌ 缓存污染
T+500ms: 同步队列执行（500ms debounce后）
T+530ms: DELETE /tasks/182 成功（数据库更新 deleted_at）
T+560ms: DELETE /tasks/183 成功

--- 用户再次点击"清空无分类" ---
T+0ms:   clearUncategorizedTasks() 开始
T+1ms:   从缓存中获取到任务182、183 ← 之前被错误添加
T+2ms:   DELETE 182 → 发送到服务器
         ❌ 服务器返回 404 Not Found（任务已在T+530ms删除）
```

### 根本原因

1. **前端采用"乐观更新 + 异步同步"模式**
   - Repository.delete() 立即从缓存移除
   - 但DELETE请求延迟执行（debounce 500ms）

2. **clearUncategorizedTasks() 返回过早**
   - 只等待操作加入队列，不等待同步完成
   - Component层无法知道DELETE是否真正执行

3. **fetchTasksByDate() 查询时DELETE未执行**
   - 数据库 deleted_at 仍为 NULL
   - 后端正确返回这些"未删除"的任务
   - 前端误以为是新任务，重新加入缓存

## ✅ 最终修复方案（2026-03-18）

### 修复策略

采用**策略1（等待确认） + 策略2（操作锁） + 策略4（请求队列）**组合：

| 策略 | 实现 | 效果 |
|------|------|------|
| **策略1：等待确认** | Store层自动等待同步队列完成 | ✅ 消除竞态条件 |
| **策略2：操作锁** | 防止并发调用 clearUncategorizedTasks() | ✅ 防止重复操作 |
| **策略4：请求队列** | 利用现有 TaskSyncQueue 机制 | ✅ 串行化DELETE请求 |

### 代码修改

#### 1. TaskRepository.waitForSync()（+54行）

**文件**: `repositories/TaskRepository.js`

```javascript
/**
 * 等待同步队列完成（用于解决DELETE和fetchTasksByDate()竞态条件）
 */
async waitForSync() {
  if (this.syncQueue.queue.length === 0) {
    return  // 队列为空，无需等待
  }

  return new Promise((resolve) => {
    const checkInterval = setInterval(() => {
      // 队列已清空且未在同步中
      if (this.syncQueue.queue.length === 0 && !this.syncQueue.isSyncing) {
        clearInterval(checkInterval)
        resolve()
      }
    }, 50)  // 每50ms检查一次

    // 超时保护（最多等待5秒）
    setTimeout(() => {
      clearInterval(checkInterval)
      resolve()  // 容错：即使超时也resolve
    }, 5000)
  })
}
```

#### 2. taskStore 操作锁 + 自动等待同步（+51行）

**文件**: `store/task.js`

```javascript
// 模块级操作锁
let clearUncategorizedLock = false

async function clearUncategorizedTasks() {
  // 操作锁：防止并发调用
  if (clearUncategorizedLock) {
    throw new Error('清空操作进行中，请稍后重试')
  }

  try {
    clearUncategorizedLock = true

    // 1. 获取无分类任务
    const uncategorizedTasks = TaskRepository.getAll().filter(...)

    // 2. 批量删除（加入队列）
    for (const task of uncategorizedTasks) {
      await TaskRepository.delete(task.id)
    }

    // 3. ⭐ 等待同步队列完成
    await TaskRepository.waitForSync()

  } finally {
    clearUncategorizedLock = false  // 解锁
  }
}
```

## 🎓 经验总结

### 竞态条件的根源

**前端"乐观更新"模式的固有问题**：

```
本地状态更新（立即） ≠ 服务器状态更新（延迟）
```

### 避免竞态条件的通用策略

1. **策略1：等待确认后更新**（本次采用）
   - 不要乐观更新，等服务器确认后再更新UI
   - 优点：彻底消除竞态
   - 缺点：用户体验稍慢

2. **策略2：操作锁**（本次采用）
   - 同一时间只允许一个操作执行
   - 优点：防止并发冲突
   - 缺点：需要处理锁状态

3. **策略3：版本号检测**（未采用，适用于多用户场景）
   - 每次操作携带版本号，服务器检测冲突
   - 优点：检测并发冲突
   - 缺点：需要修改数据库和后端

4. **策略4：请求队列**（本次采用）
   - 所有操作进入队列，按顺序执行
   - 优点：串行化操作
   - 缺点：需要等待队列完成

5. **策略5：幂等性设计**（后端已支持，未充分利用）
   - 同一个操作执行多次，结果相同
   - 优点：容错性好
   - 缺点：需要前端忽略404等错误

### 架构设计原则

1. **封装完整流程**：Store层应封装完整业务流程，Component不应知道同步细节
2. **操作原子性**：要么全部成功，要么全部失败
3. **防御性编程**：超时保护、错误处理、状态锁
4. **四层架构规范**：Component → Store → Repository → API，禁止跨层调用
