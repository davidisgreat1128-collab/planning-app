# 重复任务系统设计原则

# 一、核心设计原则

整个系统只有一句最重要的原则：

```
任务不预生成，而是按规则动态计算。
```

数据库只保存：

```
任务规则
任务执行记录
任务覆盖或删除标记
```

系统在查看某一天任务时：

```
通过规则计算任务实例
```

而不是：

```
数据库提前存好每天任务
```

------

# 二、系统的三类核心数据

整个系统围绕 **三类数据**展开：

### 1 任务规则

描述任务本身，例如：

```
任务名称
开始时间
重复规则（每天 / 每周 / 每月 /每年）
优先级
```

作用：

```
定义任务什么时候应该出现
```

------

### 2 任务执行记录

记录用户行为，例如：

```
某一天是否完成
是否跳过
完成时间
```

作用：

```
记录用户对任务的执行情况
```

注意：

```
只有执行行为才写入数据库
```

------

### 3 覆盖或删除标记

用于处理特殊情况，例如：

```
某一天修改任务属性
某一天删除任务
```

作用：

```
改变某一天任务的默认行为
```

------

# 三、任务生成逻辑（最核心算法）

当系统需要查看某一天任务时，例如：

```
2026-04-01
```

系统执行流程：

```
1 获取所有任务规则
2 判断规则是否命中该日期
3 应用删除标记
4 应用覆盖修改
5 生成任务实例
```

最终得到：

```
当天任务列表
```

这些任务实例：

```
只是计算结果
不会存入数据库
```

------

# 四、未来任务的查看方式

当用户查看未来日期，例如：

```
未来某一天
未来一周
未来一个月
```

系统做的事情完全一样：

```
根据规则计算任务
```

而不是：

```
读取数据库中已经存在的任务
```

这样可以避免：

```
数据库任务爆炸增长
```

------

# 五、系统需要支持的六种操作

重复任务系统通常需要支持 **六种用户操作**。

| 类型 | 用户操作       | 影响范围       | 实现思路             |
| ---- | -------------- | -------------- | -------------------- |
| 1    | 修改当天       | 只影响当天     | 创建**单日覆盖**     |
| 2    | 修改未来       | 当天及未来     | **拆分任务规则**     |
| 3    | 修改全部       | 整个任务       | **修改任务规则**     |
| 4    | 删除当天       | 只隐藏当天     | **单日删除标记**     |
| 5    | 完整删除任务   | 整个任务       | **删除任务规则**     |
| 6    | 删除当天及未来 | 从当天开始停止 | **修改规则结束时间** |



这些操作的核心思想是：

```
不改变历史数据
```

------

### 情况 1：修改当天

用户操作：

```
3月17
优先级 → 不紧急不重要
```

目标：

```
只改变3月17
```

实现方式：

```
创建单日覆盖
```

逻辑：

```
默认任务规则
       ↓
检查当天是否存在覆盖
       ↓
存在 → 使用覆盖
不存在 → 使用规则
```

### 情况 2：修改未来

用户操作：

```
3月17以后
优先级 → 重要且紧急
```

目标：

```
3月16及以前不变
3月17以后改变
```

实现方式：

```
拆分任务规则
```

原规则：

```
3月15开始
每天跑步
优先级：重要不紧急
```

拆分后：

```
规则A
3月15 - 3月16
优先级：重要不紧急
规则B
3月17开始
优先级：重要且紧急
```

------

### 情况 3：修改全部

用户操作：

```
整个任务
优先级 → 重要且紧急
```

目标：

```
全部规则改变
```

实现方式：

```
直接修改任务规则
```

注意：

```
历史执行记录不改变
```

------

### 情况 4：删除当天

用户操作：

```
3月17
删除今天任务
```

目标：

```
只删除这一天
```

实现方式：

```
创建单日删除标记
```

逻辑：

```
计算任务
      ↓
检查是否存在删除标记
      ↓
存在 → 不显示
不存在 → 显示
```

------

### 情况 5：完整删除任务

用户操作：

```
删除整个重复任务
```

目标：

```
任务彻底不存在
```

实现方式：

```
删除任务规则
或标记为删除
```

注意：

```
历史执行记录仍然保留
```

因为它们是：

```
历史行为数据
```

------

### 情况 6：删除当天及未来

用户操作：

```
从3月17开始
删除任务
```

目标：

```
3月16以前保留
3月17以后不存在
```

实现方式：

```
修改任务规则结束时间
```

原规则：

```
3月15开始
每天跑步
```

修改后：

```
3月15开始
3月16结束
每天跑步
```



# 六、任务计算的优先级

当系统计算某一天任务时，应该按以下顺序处理：

```
1 单日删除标记
2 单日覆盖修改
3 任务规则时间范围
4 默认任务规则
```

流程：

```
查看某一天任务
       ↓
是否删除标记？
       ↓
是 → 不显示
       ↓
否 → 是否存在覆盖？
       ↓
是 → 使用覆盖
       ↓
否 → 使用任务规则
```

------

# 七、为什么这种设计最好

这种架构有三个巨大优势。

### 1 避免数据库膨胀

如果每天生成任务：

```
任务数 × 天数 × 用户数
```

数据库会快速爆炸。

动态计算可以避免这个问题。

------

### 2 修改规则简单

当任务规则改变：

```
每天 → 每周
```

只需要：

```
修改规则
```

不需要：

```
删除大量未来任务
```

------

### 3 支持复杂操作

例如：

```
改单天
改未来
删除某一天
删除未来
```

都可以通过：

```
规则 + 覆盖
```

实现。

------

# 八、整个系统可以用一句话概括

重复任务系统本质是：

```
任务规则决定任务存在
覆盖记录改变任务属性
删除标记控制任务显示
执行记录记录用户行为
```

系统每天只是：

```
根据规则动态计算任务
```
