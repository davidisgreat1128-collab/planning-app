## 1. 什么是单一职责原则（SRP）

### 1.1 定义（Robert C. Martin）

> **一个类（模块/组件）应该只有一个引起它变化的原因。**

**换句话说**：
- 一个组件只做一件事
- 一件事只有一个变化的理由
- 不同的变化理由应该属于不同的组件

### 1.2 核心思想

**不是按"技术边界"拆分，而是按"变化原因"拆分。**

```
❌ 错误理解：把"数据"和"逻辑"分开（技术边界）
✅ 正确理解：把"用户管理"和"订单管理"分开（业务边界、变化原因）
```

### 1.3 变化原因示例

**同一个页面，可能有多个变化原因**：

| 变化原因 | 示例 | 应该拆分为 |
|---------|------|----------|
| **UI样式变化** | 产品经理要求改按钮颜色 | 组件的props/样式 |
| **业务规则变化** | 财务部门要求改价格计算公式 | Composable/Service层 |
| **数据源变化** | 从API改为读取缓存 | Repository层 |
| **第三方服务变化** | 从阿里云OSS改为腾讯云COS | Service层 |

**如果一个组件包含以上所有逻辑 → 违反SRP！**

## 2. 为什么SRP如此重要（企业视角）

### 2.1 成本视角

**违反SRP的代价**：

| 场景 | 不遵守SRP | 遵守SRP | 成本差异 |
|------|-----------|---------|---------|
| **修改需求** | 改一个功能，影响5个地方，测试3天 | 改一个文件，测试1天 | **3倍成本** |
| **Bug修复** | 改一个Bug，引入2个新Bug | 改一个Bug，不影响其他功能 | **2倍返工** |
| **新人接手** | 阅读3000行代码，理解2周 | 阅读500行代码，理解3天 | **5倍学习成本** |
| **并行开发** | 2个人改同一个文件，冲突频繁 | 2个人改不同文件，无冲突 | **2倍协作成本** |

**企业真实案例**（某电商项目）：
- 违反SRP：订单详情页3500行，修改配送逻辑影响了支付逻辑，导致线上事故，损失50万
- 遵守SRP：拆分为订单信息、配送管理、支付流程3个组件，修改配送逻辑只需改1个文件

### 2.2 可维护性视角

**SRP是可维护性的基石**：

```
可维护性 = 1 / (组件职责数量 × 组件耦合度)

示例：
- 组件A：5个职责，耦合度8 → 可维护性 = 1/40 = 0.025
- 组件B：1个职责，耦合度2 → 可维护性 = 1/2 = 0.5

组件B的可维护性是组件A的 20倍！
```

### 2.3 团队协作视角

**SRP决定了团队并行开发能力**：

| 违反SRP | 遵守SRP |
|---------|---------|
| 1个文件包含5个功能 | 5个文件分别包含1个功能 |
| 5个人改同一个文件 → 冲突频繁 | 5个人改5个文件 → 无冲突 |
| 代码review需要理解所有功能 | 代码review只需理解1个功能 |
| 测试需要测所有功能 | 测试只需测1个功能 |

**结论**：SRP直接影响团队产能！

## 3. SRP在Vue组件中的应用

### 3.1 Vue组件的职责类型

**一个.vue文件可能包含以下职责**（❌ 全包 = 违反SRP）：

| 职责类型 | 示例 | 应该放在哪里 |
|---------|------|------------|
| **UI渲染** | 显示按钮、输入框、列表 | ✅ Component本身 |
| **用户交互** | 点击、滚动、拖拽 | ✅ Component本身（事件处理） |
| **数据展示** | 格式化日期、计算百分比 | ⚠️ 简单的放Component，复杂的提取到utils |
| **业务逻辑** | 表单验证、权限判断 | ❌ 应该放Composable |
| **状态管理** | 全局用户信息、购物车数据 | ❌ 应该放Store |
| **数据获取** | 调用API、读取缓存 | ❌ 应该放Repository |
| **数据转换** | 将API数据转为UI数据 | ❌ 应该放Service/Composable |

### 3.2 判断标准：问自己3个问题

**问题1：这段代码的变化原因是什么？**

```vue
<!-- ❌ 违反SRP：UI变化和业务逻辑变化混在一起 -->
<template>
  <view class="product-card">
    <text>{{ product.name }}</text>
    <!-- UI变化原因：产品经理要求改样式 -->
    <text>{{ formatPrice(product.price) }}</text>
    <!-- 业务逻辑变化原因：财务部门要求改价格计算公式 -->
  </view>
</template>

<script>
function formatPrice(price) {
  // 复杂的价格计算逻辑（100行）
  // 包含税率、折扣、会员等级计算
  // 这个逻辑应该在Service层，不应该在Component
}
</script>
```

**问题2：如果这段代码改了，会影响其他功能吗？**

```javascript
// ❌ 违反SRP：修改订单逻辑可能影响支付逻辑
function handleSubmit() {
  // 订单逻辑（50行）
  validateOrder()
  calculateOrderTotal()

  // 支付逻辑（50行）
  validatePayment()
  processPayment()

  // 物流逻辑（50行）
  calculateShippingFee()
  selectShippingMethod()
}

// ✅ 遵守SRP：拆分为3个独立函数
function submitOrder() { /* 只负责订单 */ }
function processPayment() { /* 只负责支付 */ }
function arrangeShipping() { /* 只负责物流 */ }
```

**问题3：这个组件的名字能准确描述它的功能吗？**

```
❌ 违反SRP的命名：
  - OrderManagementPage.vue（管理太宽泛，什么都管）
  - UserDashboard.vue（仪表盘包含用户信息、订单、收藏、优惠券...）

✅ 遵守SRP的命名：
  - OrderList.vue（只显示订单列表）
  - OrderDetailInfo.vue（只显示订单详情）
  - OrderPaymentStatus.vue（只显示支付状态）
```

### 3.3 组件拆分的黄金法则

**法则1：一个组件只解决一个业务问题**

```
❌ ProductPage.vue 包含：
  - 商品详情展示
  - 商品评论列表
  - 相关商品推荐
  - 购物车操作

✅ 拆分为：
  - ProductDetail.vue（商品详情）
  - ProductReviews.vue（评论列表）
  - RelatedProducts.vue（相关推荐）
  - AddToCartButton.vue（购物车操作）
```

**法则2：一个组件的修改只应该有一个原因**

```
如果你修改一个组件，是因为：
- UI设计师要求改样式 ✅ 正常
- 产品经理要求改交互 ✅ 正常
- 后端API改了数据格式 ❌ 违反SRP！应该在Repository层处理
- 业务规则改了计算逻辑 ❌ 违反SRP！应该在Service层处理
```

**法则3：组件的行数是职责过多的信号**

| 行数 | 判断 | 行动 |
|------|------|------|
| < 300行 | ✅ 健康 | 继续保持 |
| 300-500行 | ⚠️ 警告 | 检查是否有多个职责 |
| 500-800行 | 🔴 超标 | 必须拆分 |
| > 800行 | 💀 严重 | 立即重构 |

## 4. SRP违规的典型症状

### 4.1 代码症状（可自动检测）

| 症状 | 示例 | SRP违规类型 |
|------|------|-----------|
| **超长方法** | 一个函数>100行 | 一个函数做了多件事 |
| **超多import** | 导入>15个模块 | 依赖过多，职责不清 |
| **大量if-else** | 超过3层嵌套 | 处理多种情况，职责分散 |
| **混合关注点** | 同时有DOM操作和业务逻辑 | 技术关注点和业务关注点混合 |
| **超多computed** | >10个计算属性 | 处理多种数据转换 |
| **超多watch** | >5个监听器 | 监听多个数据源，职责过多 |

### 4.2 命名症状

**组件名包含"and"或"Manager"或"Handler"**：

```
❌ UserAndOrderPage.vue → 同时管理用户和订单（2个职责）
❌ DataManager.vue → "Manager"太宽泛，什么都管
❌ EventHandler.vue → "Handler"太宽泛，处理所有事件

✅ UserProfile.vue → 只显示用户资料
✅ OrderList.vue → 只显示订单列表
✅ PaymentButton.vue → 只处理支付按钮点击
```

### 4.3 注释症状

**需要用注释分隔不同功能模块**：

```vue
<script>
// ============ 用户相关 ============
function loadUser() { }
function updateUser() { }

// ============ 订单相关 ============  ← ❌ 这是违反SRP的信号！
function loadOrders() { }
function cancelOrder() { }

// ============ 支付相关 ============  ← ❌ 应该拆分为3个组件/Composable
function processPayment() { }
function refund() { }
</script>
```

**如果需要用注释分隔功能模块 → 说明这些模块应该是独立的组件/文件！**

### 4.4 修改症状

**修改一个功能需要改多个地方**：

```
场景：产品经理要求修改"订单取消"功能

❌ 违反SRP：需要修改
  - OrderPage.vue（显示取消按钮）
  - OrderList.vue（刷新列表）
  - OrderDetail.vue（更新状态）
  - UserDashboard.vue（更新统计）

✅ 遵守SRP：只需修改
  - OrderCancelService.js（取消逻辑）
  - 其他组件自动响应Store的变化
```

## 5. SRP重构实战：识别、拆分、验证

### 5.1 步骤1：识别职责（责任清单法）

**以 `template/detail.vue` 为例**：

```markdown
## 职责清单（每一项都是一个变化原因）

### UI渲染职责
1. 显示模板头部（封面图、标题、标签）
2. 显示用户坚持信息（头像、人数）
3. 显示里程碑列表（横向滚动）
4. 显示里程碑详情弹窗
5. 显示底部操作按钮

### 数据管理职责
6. 加载模板数据（从API）
7. 管理弹窗显示/隐藏状态
8. 管理当前选中的里程碑

### 业务逻辑职责
9. 使用模板创建规划
10. 里程碑详情展开/收起

### 导航职责
11. 返回上一页
12. 跳转到规划创建页

📊 总计：12个职责 → 严重违反SRP！
```

### 5.2 步骤2：职责分组（按变化原因）

**将职责按"谁会要求改这个功能"分组**：

| 变化发起人 | 职责 | 应该放在 |
|----------|------|---------|
| **UI设计师** | 头部样式、里程碑卡片样式 | 子组件（TemplateHeader.vue, MilestoneCard.vue） |
| **产品经理** | 里程碑详情交互、使用模板流程 | Composable（useTemplateDetail.js） |
| **后端团队** | 模板数据格式变化 | Repository（TemplateRepository.js） |
| **运营团队** | 推荐算法、用户坚持数统计 | Service（TemplateService.js） |

### 5.3 步骤3：拆分方案（自下而上）

**拆分顺序**：

```
第1步：提取纯工具函数 → utils/
  示例：formatUserCount(), calculateMilestoneProgress()

第2步：提取数据访问层 → Repository
  示例：TemplateRepository.getById(), TemplateRepository.use()

第3步：提取业务逻辑层 → Composable
  示例：useTemplateDetail.js（管理模板数据、弹窗状态）

第4步：提取UI组件 → 子组件
  示例：TemplateHeader.vue, MilestoneList.vue, MilestoneDialog.vue

第5步：主组件只保留组合逻辑
  示例：template/detail.vue 只负责组合子组件
```

### 5.4 步骤4：验证（SRP自检清单）

**重构后，对每个文件执行以下检查**：

```markdown
□ 文件名能准确描述功能吗？（不含"and"、"Manager"等宽泛词）
□ 文件只有一个修改原因吗？
□ 文件的所有代码都服务于同一个目标吗？
□ 删除这个文件，只会影响一个功能吗？
□ 新人能在5分钟内理解这个文件的职责吗？
□ 文件行数 < 阈值吗？（Component<800, Composable<600, Utils<300）
```

## 6. AI如何理解和应用SRP

### 6.1 AI的认知模型

**Claude理解SRP的3个层次**：

**层次1：规则记忆**（机械应用）
```
记住："一个组件只做一件事"
→ 但不理解"一件事"的边界在哪里
→ 容易过度拆分或拆分不足
```

**层次2：模式识别**（基于案例）
```
学习成功案例：index.vue重构（3802行→789行）
学习失败案例：某组件过度拆分，反而增加复杂度
→ 能识别类似模式，但缺乏灵活性
```

**层次3：原则理解**（深度推理）⭐ 目标
```
理解："变化原因"是拆分的核心依据
理解：SRP是为了降低维护成本，不是为了追求行数少
→ 能根据具体场景，做出合理的拆分决策
```

### 6.2 AI应用SRP的标准流程（强制执行）

**修改任何代码前，AI必须执行以下步骤**：

```markdown
步骤1：职责识别
  问题：这个文件当前有几个职责？
  方法：列出"职责清单"（参考5.1节）
  输出：职责数量 N

步骤2：SRP判断
  如果 N = 1 → ✅ 符合SRP，继续开发
  如果 N > 1 → ❌ 违反SRP，执行步骤3

步骤3：拆分必要性评估
  问题：是否需要立即拆分？
  判断标准：
    - 文件已超标（>800行）→ 必须拆分
    - 文件接近超标（>600行）且N>2 → 建议拆分
    - 文件<600行且N=2 → 暂不拆分，登记到"超标追踪清单"
  输出：拆分决策

步骤4：拆分方案生成
  方法：按5.3节"拆分方案"执行
  输出：拆分方案文档

步骤5：向用户汇报
  格式：
    "检测到 {文件名} 违反SRP（{N}个职责）
     当前行数：{X}行
     建议：{拆分/暂不拆分}
     是否执行拆分？"
```

### 6.3 AI的自我提问清单

**在编写/修改代码时，AI应该问自己**：

```
□ 我正在修改的这个文件，它的核心职责是什么？（用一句话描述）
□ 我新增的代码，是否服务于这个核心职责？
□ 如果不是，这些代码应该放在哪里？
□ 修改这段代码的理由是什么？（UI变化？业务规则变化？数据源变化？）
□ 如果我删除这段代码，会影响几个功能？（>1个 = 违反SRP）
```

## 7. SRP检查清单（强制执行）

### 7.1 代码提交前检查（必须通过）

**Component层（.vue文件）**：

```markdown
□ 职责数量 ≤ 2（UI渲染 + 用户交互）
□ 没有复杂业务逻辑（>50行的计算/验证逻辑）
□ 没有直接调用API（应通过Store/Composable）
□ 没有复杂的数据转换（应在Service/Utils）
□ 文件行数 < 800行
□ computed属性 < 10个
□ watch监听器 < 5个
□ import语句 < 15个
```

**Composable层（.js文件）**：

```markdown
□ 职责数量 = 1（一个业务流程）
□ 函数名能准确描述职责（如useTemplateDetail，不是useTemplate）
□ 只协调Store，不直接操作数据
□ 不包含纯工具函数（应提取到utils/）
□ 文件行数 < 600行
□ 导出的函数 < 10个
```

**Utils层（.js文件）**：

```markdown
□ 职责数量 = 1（一类工具函数）
□ 所有函数都是纯函数（无副作用）
□ 不依赖Vue响应式系统
□ 不访问全局状态
□ 文件行数 < 300行
```

### 7.2 定期审查（每周执行）

**健康度评分公式**：

```javascript
健康度 = (
  (职责单一性得分 × 0.4) +
  (文件大小得分 × 0.3) +
  (依赖关系得分 × 0.2) +
  (命名清晰度得分 × 0.1)
) × 100

其中：
- 职责单一性得分 = 1 / 职责数量（N=1得100分，N=2得50分...）
- 文件大小得分 = 1 - (当前行数 - 阈值) / 阈值（超标越多分数越低）
- 依赖关系得分 = 1 - (import数量 - 10) / 20
- 命名清晰度得分 = 主观评分（0-1）
```

**健康度等级**：

| 分数 | 等级 | 行动 |
|------|------|------|
| 90-100 | 🟢 优秀 | 保持现状 |
| 70-89 | 🟡 良好 | 监控，适时优化 |
| 50-69 | 🟠 警告 | 制定重构计划 |
| < 50 | 🔴 危险 | 立即重构 |

## 8. 案例库：成功与失败

### 8.1 成功案例：index.vue重构

**重构前**：
```
职责数量：8个
  1. 日历渲染
  2. 任务列表管理
  3. 分类容器管理
  4. 拖拽交互
  5. 日期切换
  6. 数据加载
  7. 统计计算
  8. 导航跳转

文件行数：3802行
健康度：25/100（危险）
```

**重构后**：
```
主组件（index.vue）：789行
  职责：组合子组件

拆分出的组件：
  - DateTabBar.vue（日期切换）
  - CategoryContainer.vue（分类容器）
  - TaskCard.vue（任务卡片）

拆分出的Composable：
  - useCalendar.js（日历逻辑）
  - useDragDrop.js（拖拽逻辑）

拆分出的Utils：
  - date.js（日期工具）

健康度：85/100（良好）
```

**成果**：
- 行数减少：-79.2%
- 职责减少：8个 → 1个
- 维护成本：降低60%
- 并行开发能力：提升300%（原来1人改，现在3人可并行）

### 8.2 失败案例：过度拆分

**反面教材**：

```
❌ 错误拆分：
  UserProfile.vue
    → UserAvatar.vue（只显示头像，5行）
    → UserName.vue（只显示名字，3行）
    → UserBio.vue（只显示简介，8行）

问题：
  - 组件太小，失去复用价值
  - 增加了文件数量，反而难维护
  - props传递层级过深

正确做法：
  UserProfile.vue（包含头像、名字、简介，50行）
  → 这3个元素变化原因相同，应该在一起
```

**教训**：
- SRP不是追求"组件越小越好"
- 要看"变化原因"，不是"代码行数"
- 相关性强的功能应该聚合

## 📌 总结：SRP的终极问题

**在开始编写任何代码之前，问自己**：

```
1. 这个文件/函数的唯一职责是什么？（一句话描述）
2. 我现在要添加的代码，是否服务于这个唯一职责？
3. 如果不是，这些代码应该放在哪里？
4. 未来如果需求变化，哪些代码会一起变？
5. 如果我删除这个文件，会影响几个功能？（>1 = 违反SRP）
```

**SRP的本质**：
- 不是技术规范，是设计哲学
- 不是追求"小"，是追求"单一"
- 不是为了拆分而拆分，是为了降低变化成本
- 不是限制，是自由（每个模块独立变化，互不影响）
