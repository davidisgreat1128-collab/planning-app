### 4. 核心问题诊断

#### 问题1: 违反DRY原则（Don't Repeat Yourself）

**症状**: 85%的代码逻辑重复

**影响**:
- 修改一个功能需要同时修改两个文件
- Bug修复容易遗漏其中一个文件
- 新增功能需要写两遍代码

**证据示例**:

```javascript
// task-edit.vue 第760-763行
const subtasks = ref([]);
const newSubtaskText = ref('');
function addSubtask() {
  if (!newSubtaskText.value.trim()) return;
  subtasks.value.push({
    title: newSubtaskText.value.trim(),
    done: false
  });
  newSubtaskText.value = '';
}

// AddTaskPanel.vue 第601-606行（几乎完全相同）
const subtasks = ref([]);
const subtaskDraft = ref('');
function addSubtask() {
  if (!subtaskDraft.value.trim()) return;
  subtasks.value.push(subtaskDraft.value.trim());
  subtaskDraft.value = '';
}
```

#### 问题2: 未遵循三层架构

**症状**: 业务逻辑直接写在UI组件内

**影响**:
- 无法在其他页面复用任务表单逻辑
- 测试困难（需要挂载整个组件）
- Store层功能单薄（只做CRUD，无业务封装）

**证据**:
```javascript
// 两个文件都直接调用 taskStore.createTask()
// 没有中间的业务逻辑层
async function submit() {
  const data = {
    title: form.value.title,
    isUrgent: form.value.isUrgent,
    isImportant: form.value.isImportant,
    // ... 20+个字段的组装逻辑
  };
  await taskStore.createTask(data);
}
```

**标准三层架构应该是**:
```
Component (UI层)
  → useTaskForm() (Composable业务逻辑层)
    → taskStore (Store状态层)
      → taskRepository (Repository数据层)
```

#### 问题3: 样式代码占比过高

**症状**: 样式代码占60%以上

| 文件 | 样式行数 | 总行数 | 占比 |
|------|---------|--------|------|
| task-edit.vue | ~1540行 | 3340行 | 46% |
| AddTaskPanel.vue | ~1447行 | 2847行 | 51% |

**影响**:
- 查找业务逻辑困难
- 样式修改容易破坏逻辑代码
- 文件加载性能下降

#### 问题4: 缺少可复用组件

**症状**: 相同UI元素重复编写

**重复的UI组件**（可提取为独立组件）:
- ✅ 日期Tab栏（100%重复）
- ✅ 子计划列表（95%重复）
- ✅ 四象限选择器（100%重复）
- ✅ 时间段选择器（90%重复，已有H5/App分端逻辑）
- ✅ 分类选择器（100%重复）

## 💊 重构方案建议

### 方案A: 提取公共业务逻辑层（推荐 ⭐⭐⭐⭐⭐）

**核心思路**: 将85%重复的业务逻辑提取为 `useTaskForm()` Composable

**架构设计**:
```
┌─────────────────────────────────────────────────────────┐
│  UI层（Component）                                       │
│  ├── task-edit.vue (全屏页面)      → 500行              │
│  └── AddTaskPanel.vue (底部面板)   → 400行              │
└────────────────┬────────────────────────────────────────┘
                 ↓ 调用
┌─────────────────────────────────────────────────────────┐
│  业务逻辑层（Composable）                                │
│  └── useTaskForm.js                 → 600行              │
│      ├── 表单数据管理 (form, subtasks, ...)             │
│      ├── 表单验证逻辑 (validate)                         │
│      ├── 提交逻辑 (submit, update, delete)              │
│      └── 工具函数 (formatDate, calcDuration, ...)       │
└────────────────┬────────────────────────────────────────┘
                 ↓ 调用
┌─────────────────────────────────────────────────────────┐
│  状态管理层（Store）                                     │
│  └── store/task.js                  → 300行              │
│      ├── 计算属性 (tasks, filteredTasks, ...)          │
│      └── Actions (createTask, updateTask, deleteTask)    │
└────────────────┬────────────────────────────────────────┘
                 ↓ 调用
┌─────────────────────────────────────────────────────────┐
│  数据访问层（Repository）                                │
│  └── repositories/TaskRepository.js → 400行              │
│      ├── memoryCache (Map)                              │
│      ├── localStorage (持久化)                          │
│      └── 服务器同步 (sync)                              │
└─────────────────────────────────────────────────────────┘
```

**预期收益**:
- ✅ 消除85%的代码重复（减少约1700行重复代码）
- ✅ task-edit.vue 从3340行 → ~900行（含样式）
- ✅ AddTaskPanel.vue 从2847行 → ~800行（含样式）
- ✅ 新增 useTaskForm.js ~600行（可复用）
- ✅ 遵循三层架构规范
- ✅ 测试覆盖率提升（可单独测试useTaskForm）

**实施难度**: 🟡 中等（需要重构两个大文件，预计8小时）

**风险评估**: 🟢 低风险（逻辑抽取后行为不变，可逐步迁移）

---

### 方案B: 提取可复用UI组件（辅助方案 ⭐⭐⭐⭐）

**核心思路**: 将重复的UI元素提取为独立组件

**新增组件清单**:

| 组件名 | 路径 | 功能 | 预计行数 | 复用场景 |

| `CategoryPicker.vue` | `components/task/CategoryPicker.vue` | 分类选择器 | ~250行 | task-edit、AddTaskPanel |

**预期收益**:
- ✅ 减少UI代码重复（约800行）
- ✅ 组件可在其他页面复用
- ✅ 样式统一，修改一处生效全局

**实施难度**: 🟢 简单（逐个提取，不影响现有功能）

**风险评估**: 🟢 低风险（独立组件，易于测试）

### 方案C: 合并两个文件为统一组件（不推荐 ⭐⭐）

**核心思路**: 将task-edit.vue和AddTaskPanel.vue合并为一个TaskFormComponent.vue，通过props控制显示模式

**缺点**:
- ❌ 单文件会超过4000行，更难维护
- ❌ 逻辑耦合更严重（全屏模式 vs 面板模式）
- ❌ 违反单一职责原则

**不推荐理由**: 增加复杂度，不解决根本问题
